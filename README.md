# cc-container-yard

管理箱位、堆叠关系、场内移动任务，以及集装箱进出场预约（闸口时段、堆位预留、出场前置移箱整体协调）。

## 主要业务规则

### 堆场与移箱

- **堆位建模**：堆场由多个堆栈（`YardStack`）组成，每个堆栈有最大层数与最大总重量；
  集装箱（`Container`）有全局唯一箱号、重量和当前位置（所属堆栈 + 层号），
  同一堆栈内层号唯一（数据库唯一约束 `uk_container_stack_tier`）。
  堆栈额外维护 `reservedTiers/reservedWeight`：已被进场预约预留但尚未实际落位的容量，
  移箱的模拟与执行都会把预留量计入容量判断，不会压住已预留的堆位。
- **可移动性**：只有位于栈顶的箱可以移动；目标堆栈加入该箱后不能超过层数或重量上限（含预留）；
  不允许移动到箱当前所在的堆栈。
- **计划校验**：移箱计划由按顺序执行的步骤组成（箱号 + 目标栈）。提交计划时在内存中
  完整模拟全部步骤：逐步校验源箱处于（模拟后的）栈顶、目标堆栈存在且容量足够，
  同一箱在步骤间的位置保持连续。任一步失败则整份计划不保存（HTTP 422）。
- **版本快照**：计划保存时记录所有涉及堆栈（源栈与目标栈）的 `@Version` 版本快照。
- **安全执行**：执行在单一事务中完成——先对计划行加悲观写锁（保证重复执行幂等），
  再按堆栈编码排序对相关堆栈加悲观写锁（避免死锁），逐一比对版本快照；
  任一堆栈版本已变化则整份计划标记为 `STALE_REJECTED` 并拒绝（HTTP 409），
  不会执行部分步骤。校验通过后重放全部步骤，一次性更新位置、重量、层级与版本，
  并写入不可变的移动事件（`MoveEvent`）。
- **幂等与并发**：重复执行同一计划返回原结果，不产生重复事件；两个计划并发修改
  共享堆栈时，数据库行锁 + 版本比对保证最多一个基于同一版本成功，另一个按陈旧拒绝。
  并发控制依赖 JPA 悲观锁与乐观版本（数据库层面），不依赖进程内锁。

### 闸口预约（进出场整体协调）

- **闸口时间窗**：`GateWindow` 为 `[startAt, endAt)` 的时间窗，配置可处理车辆数 `capacity`。
  窗口维护 `reserved`（已批准预约名额）与 `served`（已完成到场名额）；时间窗之间不允许重叠。
- **预约申报**：预约声明预约业务号、箱号、方向（`INBOUND`/`OUTBOUND`）、车牌、时间窗
  及（进场）目标堆栈与箱重。一个箱同一时间只能存在一笔有效预约
  （`active_container_no` 唯一约束 + 申报前检查双重保证）。
  - 进场：箱必须尚不在场内，必须声明目标堆栈与正数箱重；
  - 出场：箱必须已在场内，箱重取场内记录，不允许声明目标堆栈。
- **批准是一次原子协调**（单事务，加锁顺序固定为「预约 → 闸口时段 → 箱 → 堆栈」）：
  - 进场：同时预留闸口名额与目标堆位（同时校验剩余高度与重量）；
  - 出场：基于当前堆叠关系生成必要的前置移箱计划（把压在目标箱上方的箱逐个搬到
    按编码排序、第一个可容纳的缓冲堆栈），计划带堆栈版本快照并关联预约号；
    目标箱已在栈顶时无前置计划。
  - 闸口满、堆位高度/重量不足、或前置移箱无处安置时，**整笔预约失败**：事务回滚，
    预约保持 `PENDING`，不留下任何名额或堆位占用，稍后可重试批准。
- **到场确认**：必须携带预约版本号、到场业务号和到场时间，逐一校验：
  - 预约必须已批准；预约版本必须与当前一致（否则 409，拒绝旧客户端指令）；
  - 到场时间必须落在预约时间窗内；
  - 校验箱的实际位置（进场箱不得已在场内；出场箱必须在场内）。
  - 进场：预留转为实际占用，箱落目标堆栈栈顶，闸口名额由 reserved 结转为 served；
  - 出场：若堆场布局在批准后已变化导致旧前置计划版本快照陈旧，**旧计划绝不执行**，
    按当前布局重新规划并立即执行，然后提箱出场；重新规划失败时预约保持 `APPROVED`
    （返回 `NEEDS_MANUAL` / HTTP 409），等待人工处理，人工处理后按新版本可再次到场。
    若箱已自然到顶，旧前置计划作废且不执行。
- **取消与幂等**：预约、到场、取消各用独立业务号（分别唯一）。
  - 同一预约号重复申报返回原预约；同到场号/取消号重复提交幂等返回；不同业务号作用于
    已终结的预约返回 409。
  - 取消只释放一次资源：回退闸口名额，进场回退堆位预留，出场作废未执行的前置计划；
    已到场的预约不可取消。
  - 并发批准由闸口时段与堆栈行上的悲观写锁串行化，保证不突破闸口容量、不重复占箱、
    不产生孤立堆位预留。

## API 概览

### 堆场与移箱

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/yard/layout` | 堆场布局（容量、实际/预留占用、版本、箱列表） |
| POST | `/api/stacks` | 新建堆栈 `{code, maxTiers, maxWeight}` |
| POST | `/api/containers` | 箱入场 `{containerNo, weight, stackCode}`（放到栈顶） |
| POST | `/api/plans/simulate` | 模拟计划，返回逐步校验结果，不落库 |
| POST | `/api/plans` | 校验并保存计划（含版本快照），失败返回 422 |
| GET | `/api/plans/{id}` | 查询计划详情 |
| POST | `/api/plans/{id}/execute` | 执行计划；陈旧计划返回 409 |
| GET | `/api/events?planId=` | 查询移动事件（可按计划过滤） |

### 闸口与预约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/gate/windows` | 新建时间窗 `{startAt, endAt, capacity}`（不允许重叠） |
| GET | `/api/gate/schedule?from=&to=` | 闸口日程（可按时间范围过滤） |
| POST | `/api/appointments` | 申报预约（幂等：同一 appointmentNo 返回原预约） |
| POST | `/api/appointments/{no}/approve` | 批准：原子预留闸口+堆位 / 生成出场前置移箱计划 |
| POST | `/api/appointments/{no}/arrivals` | 到场确认 `{arrivalNo, expectedVersion, at}` |
| POST | `/api/appointments/{no}/cancel` | 取消预约 `{cancelNo}`，资源只释放一次 |
| GET | `/api/appointments` | 预约列表 |
| GET | `/api/appointments/{no}` | 预约详情（含关联前置移箱计划、版本号） |
| GET | `/api/appointments/{no}/plan` | 出场预约的前置移箱步骤与版本快照 |
| GET | `/api/occupancy/windows/{windowId}` | 闸口时段资源占用（名额 + 关联有效预约） |
| GET | `/api/occupancy/stacks/{stackCode}` | 堆位资源占用（预留量 + 关联进场预约） |

到场确认返回体：`outcome` 为 `ARRIVED`（成功，可能 `replanned=true`）或
`NEEDS_MANUAL`（旧计划陈旧且重排失败，预约保留等待人工，HTTP 409）。

### 典型流程

1. `POST /api/gate/windows` 配置时间窗容量；
2. `POST /api/appointments` 申报进/出场预约；
3. `POST /api/appointments/{no}/approve` 批准（进场预留名额+堆位；出场生成前置移箱计划）；
4. 车辆到场：`GET /api/appointments/{no}` 取版本号 → `POST .../arrivals` 确认；
5. 必要时 `POST .../cancel` 取消（幂等）。
